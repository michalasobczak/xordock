# Security analysis — round S007 (2026-11-22)

**Scope:**
- the `macos/` app (SwiftUI), CLI JSON commands, `vault.Peek`, the build script;
- regressions against S001–S005;
- owner reports from tests on USB sticks (typo in `--card`, `sudo`, slow writes).

## Result

Two gaps fixed in this round (R7-01, R7-03). One high finding was moved to a separate spec, S006 (R7-02). Share format unchanged; no S004 and S005 regressions: `go test -race ./...` is green.

| ID | Severity | Finding | Status |
|---|---|---|---|
| R7-01 | medium | `--name` was not validated. `--name ../x` placed A outside `Application Support/xordock`, B outside `<card>/xordock`, and the mount point outside `/Volumes`. The bug has existed since S001. An app with a text field would have made it more prominent. | **fixed**: `validName` in the CLI (`--name`, `--new-name`) and `VaultName.validate` in the UI. Tests `TestValidName`, `vaultNameValidation`, `realCLIVolumesDecode`. |
| R7-02 | high | The "A and B on different media" check compares the volumes' `st_dev`. A `.dmg` image stored on the SSD passed as a card (confirmed). A second partition of the same disk would pass too. A check error is ignored (fail-open) and leaves the A header behind. The check does not run on `Open`. | **open → S006** (owner decisions gathered). Mitigation in the UI: volumes on the system disk (`systemDisk`) are not offered as a card. |
| R7-03 | low | `CLI.locate` accepted `XORDOCK_CLI` and `bin/xordock` from the working directory also inside the `.app` bundle. | **fixed**: inside the bundle only `Contents/Resources/xordock`. Test `bundledAppIgnoresEnvOverride`. |
| R7-04 | low | The app is ad hoc signed, without sandbox and hardened runtime. A malicious program with user privileges can replace the CLI in the bundle. | **accepted**: outside the threat model (S004: local malware with user privileges reads the mounted volume and both sides anyway while the card is connected). |
| R7-05 | low | `Peek` reads without a lock. The mounting process's GC may delete the index being read. | **accepted**: objects are immutable, so the effect is a "details unavailable" error, not a false state. `ErrBusy` when the superblocks differ. |
| R7-06 | low | The mount survives the app being closed (S007 requirement), so a vault may stay mounted "silently". | **accepted**: `lock.open` icon after relaunch; removing the card unmounts anyway. |
| R7-07 | low | Running the CLI via `sudo` leaves A files owned by root (owner report). With a typo in `--card` it creates a directory in `/Volumes` on the system disk. | **open → S006** (proposal to refuse running as root). The app never uses `sudo`. |

## Checked with no findings

- **No shell (G4):** Swift code only runs `Process` with an argument array. A test scans the sources for `/bin/sh`, `bash`, `zsh` and `-c`.
- **UI does not touch the shares (G5):** Swift code does not read vault directories. State comes from the CLI's JSON, and plaintext never passes through the app.
- **Mount log (CG-12):** contains CLI messages (vault name, mount point, warnings), without file names. The directory has mode 0700, the file 0600.
- **Writing to media (S004 §7):** every write to a medium requires the user's choice in a sheet (wizard, backup, restore). The app creates nothing automatically.
- **JSON:** `volumes` reveals only vault names and identifiers from the headers (like F-05), without file names.

## Status of earlier findings

Unchanged since round S004: R4-03 open and mitigated, F-03–F-08 as before. New observations, outside security:
- writing through the vault on a slow USB 2.0 stick was ~4× slower than writing directly (0.8 vs 3.7 MB/s);
- a candidate for a separate performance spec.
